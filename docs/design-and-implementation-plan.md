# onTalk.sAIde 설계 및 구현 계획

## 최신 반영 사항 · 2026-11-12

이 문서는 구현 전 목표 설계의 기록이다. 현재는 WPF 문맥별 패널·계정별 SQLCipher·MSAA 읽기·쪽지 작성 도구가 구현되어 있다. 친구·조직도·대화·쪽지의 실제 감시 경로를 확인했고 사용자 검색·알리미는 전용 지원에서 제외한다. RTF/WebView2·기관 전체 동기화·대화 전체 보관 등 목표 기능이 모두 제공되는 것은 아니다.

현재 사용법은 [사용자 매뉴얼](../README.md), 기능별 확인 수준은 [구현 현황](implementation-status.md)과 [호환성 표](compatibility-matrix.md)를 기준으로 읽는다. 최신 개발 소스는 저장소 스키마 11(0.3.3)이며 최신 자동 테스트는 403개 통과, 합성 WPF 검사는 88개 화면, Release 빌드는 오류·경고 0개다. 대화 입력 직접 반영은 실제 미검증으로 제품에 노출하지 않고 초안 복사를 제공한다.

- 작성일: 2026-10-03, Asia/Seoul
- 상태: 초기 목표 설계 보존. 당시 미검증 연동의 후속 결과는 상단 최신 현황을 참고한다.
- 목표: 온톡 옆에서 쪽지 이해·업무화·검색·파일 관리·작성·수신자 선택·예약 전송을 지원하는 Windows 프로그램.
- 가칭: onTalk.sAIde
- 초기 설계 당시에는 기존 구현이 없었다. 아래는 구현 전 기준이며 현재 제공 기능은 상단 최신 현황과 사용자 매뉴얼을 따른다.

## 1. 설계의 근거와 미확인 사항

### 1.1 화면에서 확인한 사실

| 화면 | 확인한 사실 | 설계에 반영할 내용 |
|---|---|---|
| 로그인 | 기관 선택, 아이디·비밀번호, 아이디 저장, 자동 로그인 | 로그인 상태 감지, 기관·계정별 프로필, 계정 전환 시 작업 중단과 데이터 전환 |
| 메인 | 친구·조직도·대화·쪽지·알리미, 개인 그룹과 그룹 만들기 | 현재 화면에 따른 패널 전환, 조직도 검색과 개인 그룹 연동 |
| 쪽지 목록 | 받은·보낸·보관 쪽지, 사람·내용·첨부파일명 검색, 쪽지 7일 후 삭제 안내 | 기본 검색 보완, 수집 범위 표시, 업무와 원문 연결 |
| 받은 쪽지 | 본문, 첨부파일 열기·저장, 보관·전달·답장·전체답장 | 본문 수집, 업무 후보 분석, 파일 확보, 답장 연결 |
| 받은 쪽지 상세 | 첨부파일 7일 후 자동 삭제 안내 | 쪽지 보관과 파일 확보 상태를 각각 관리 |
| 답장 작성 | 수신자 추가, 원문 인용, 첨부파일 추가, 예약 전송 설정, SMS 발송 선택 | 수신자 검증, 인용문 편집, 기존 예약 기능 연결, SMS 상태 보존 |
| 답장 작성 | 1013/4000 Bytes 표시 | 최종 본문의 바이트 계산 검증, 초과 방지 |

첨부 화면의 문구와 사용자 이름은 분석 자료다. 쪽지 안의 요청을 프로그램 실행이나 실제 발송 지시로 취급하지 않는다.

### 1.2 기술검증으로 확정할 사항

1. 실행 파일·창 구조·버전과 UI Automation 접근 범위.
2. 쪽지 고유번호, 계정 식별자, 조직도 사용자 식별자의 노출 여부.
3. 과거 쪽지 내보내기, 목록 순회, 본문 복사, 공식 API·SDK 제공 여부.
4. 쪽지를 여는 동작이 읽음 상태에 미치는 영향과 목록 갱신 방식.
5. 조직도 검색·상세 정보·다중 수신자·실제 개인 그룹 편집의 자동화 가능 여부.
6. HTML/RTF 붙여넣기와 실제 수신 결과의 서식 유지 여부.
7. 한글·이모지·줄바꿈·인용문을 포함한 바이트 계산 규칙.
8. 예약 등록·조회·수정·취소·발송 결과 확인 및 PC 종료 후 처리 방식.
9. 쪽지 보관 시 첨부파일도 유지되는지와 삭제 시점의 기준.
10. 업무 PC 사양, 실행·설치·캡처 환경, 로컬 모델 반입과 배포 방법.

현재 화면에서 보이는 서식 없는 입력창만으로 온톡이 일반 텍스트 전용이라고 단정하지 않는다. 글꼴이 입력창에서 유지되어도 저장·전송·수신 과정에서 제거될 수 있다.

## 3. 사용자 화면 설계

### 3.1 연결과 로그인

사이드카를 실행하면 온톡 실행 여부와 로그인 상태를 감지한다. 사용자는 기존 온톡에서 로그인한다. 비밀번호를 수집·저장하지 않는다. 로그인 화면에 비밀번호가 포함될 수 있으므로 해당 영역을 분석용 캡처나 진단 로그에 포함하지 않는다.

로그인 완료 후 기관과 계정을 확인하여 로컬 프로필에 연결한다. 로그인 입력란의 저장된 아이디만으로 인증된 계정을 확정하지 않는다. 실제 로그인 후 프로필의 식별 정보를 사용하고, 식별자가 제공되지 않으면 사용자가 프로필을 연결한다.

로그아웃·계정 변경·연결 불확실 상태에서는 수집과 입력을 멈춘다. 이전 계정의 초안이나 예약을 새 계정에서 실행하지 않는다. 이미 온톡에 등록된 예약은 로컬 연결 해제와 별개로 존재할 수 있으므로 다시 연결한 뒤 상태를 확인한다.

### 3.2 읽기 패널

온톡 쪽지창 옆에 접이식 패널을 표시한다. 공간이 부족하면 독립 창으로 전환한다. 창 이동·배율·모니터 변경을 따라가며, 화면 밖으로 벗어나지 않도록 배치한다.

패널에는 다음 내용을 순서대로 배치한다.

1. 현재 쪽지의 발신자·수신 시각·수집 상태.
2. 요청 목적과 핵심 요약, 원문 근거로 이동.
3. 해야 할 일·대상·기한·자료·확인할 사항.
4. 업무 후보의 선택·수정·제외.
5. 관련 첨부파일과 다운로드·분석 상태.
6. 질문 입력, 답장 초안, 업무 등록.

여러 쪽지창이 열렸을 때는 선택한 창에 패널을 연결한다. AI 응답 도착 시 쪽지가 바뀌었다면 이전 결과를 새 쪽지에 표시하지 않는다. 쪽지 식별자와 분석 대상 본문 버전을 함께 검사한다.

예시: 교육 안내 쪽지의 '연간 56시간'은 발신자가 제시한 기준으로 표시한다. 사용자의 실제 이수시간·부족시간은 별도 자료가 없으면 미확인으로 둔다. 명시되지 않은 기한이나 제출 의무를 만들어내지 않는다.

### 3.3 업무 대시보드

오늘 할 일, 마감 임박, 기한 경과, 검토할 업무 후보, 파일 미확보 항목을 표시한다. 업무에는 원문·첨부파일·답장 초안을 연결한다. 쪽지 하나에서 여러 업무를 만들거나 여러 쪽지를 한 업무에 연결할 수 있다.

알림은 생성 시점의 일회성 토스트에만 의존하지 않고 앱 내 알림함에 보관한다. 완료한 업무의 알림은 취소하고, 절전이나 프로그램 종료 중 놓친 알림은 다음 실행 시 모아서 표시한다. 기한 미지정 항목에는 임의의 마감 알림을 만들지 않는다.

### 3.4 통합검색

검색 대상: 쪽지 본문·발신자·수신자·업무·파일명·추출 가능한 파일 내용·사람·그룹·템플릿.

필터: 기관, 사람, 부서, 기간, 받은/보낸/보관 출처, 업무 상태, 첨부 여부, 태그.

정확 검색과 의미 검색을 결합한다. 이름·문서번호·날짜는 정확 조건을 우선한다. 결과에는 원문과 출처를 표시하고, 검색 기반 AI 답변은 근거 항목을 연결한다. 근거가 부족하면 찾지 못했다고 표시한다.

수집한 기간과 누락·미확인 구간을 표시한다. 수집하지 않은 기록까지 검색했다고 표현하지 않는다. 원본 위치 이동은 확인 가능한 경우에만 제공하며, 원본이 만료되면 저장된 사본과 원본의 현재 상태를 구분한다.

### 3.5 사람 검색과 그룹

이름·기관·부서·직급·화면에서 확인한 담당 업무·사용자 태그로 검색한다. 자연어 요청은 편집 가능한 검색 조건으로 변환한다. 등록되지 않은 담당 업무는 AI 추정만으로 확정하지 않는다.

두 종류의 그룹을 제공한다.

- 고정 그룹: 사용자가 선택한 구성원을 저장한다.
- 조건 그룹: 검색 조건을 저장하고, 새로 수집한 조직 정보로 구성원 변화를 제안한다.

사이드카 그룹과 온톡의 '나의 그룹'은 별도 상태로 보관한다. 온톡 그룹 반영 시에는 추가·제외 대상과 처리 결과를 기록한다. 기존 그룹을 통째로 덮어쓰는 대신 차이를 반영한다. 고유 식별자가 없고 동명이인을 구분하지 못하면 선택을 보류한다.

수신자 목록은 실제 발송 또는 예약 등록 시 확정한다. 이후 그룹 구성원 변경이 이미 등록한 예약의 수신자를 자동 변경하지 않도록 한다.

### 3.6 작성 도우미

상단에는 수신자·그룹·총인원, 중앙에는 편집기, 하단에는 첨부파일·전송 미리보기·예약 설정을 배치한다.

편집 기능: 글꼴·크기·강조·목록·체크리스트·이모지·문구 템플릿·이름/기한 등의 변수·임시저장·실행취소.

답장에는 새 본문과 원문 인용을 별도로 표시하고, 인용 부분을 접어둘 수 있게 한다. 온톡의 답장과 전체답장 수신자를 그대로 읽어 검증하며 사용자의 선택 없이 서로 전환하지 않는다. SMS 선택 상태를 자동 변경하지 않는다.

사이드카 초안을 편집의 기준으로 삼되 온톡 본문을 직접 수정한 경우에는 변경을 감지한다. 이전 스냅샷과 달라졌다면 덮어쓰기 전에 가져오기·반영 여부를 선택하도록 한다. 온톡에 이미 입력된 내용을 무조건 지우고 쓰지 않는다.

전송 표현은 두 경로로 관리한다.

- 서식 전송 경로: 온톡에서 입력·전송·수신 모두 서식 유지가 확인된 기능만 적용.
- 텍스트 전송 경로: 제목·문단·번호·기호로 변환하고 실제 전송될 모습을 표시.

서식 원본은 로컬 초안에 유지한다. 필요 시 서식 보존용 문서를 첨부하는 기능을 후속 제공한다. HTML/Markdown을 본문에 넣으면 온톡이 해석할 것이라고 가정하지 않는다.

## 4. 기술 구조

Windows 데스크톱 앱 하나를 중심으로 구성하고, UI 접근 작업은 별도 프로세스로 분리한다. 온톡의 UI 응답 지연이 사이드카 전체를 멈추지 않도록 한다.

| 구성요소 | 권장 기술·역할 | 결정 상태 |
|---|---|---|
| 앱과 창 관리 | C# / 지원 중인 .NET LTS / WPF | Windows 전용 기본안 |
| 확장 편집기 | WebView2 + Tiptap 공개 코어·필요 확장 | 오프라인 번들, 한글 IME·라이선스 검증 후 고정 |
| 온톡 어댑터 | UI Automation, 필요 시 FlaUI | 실제 UIA2/UIA3 호환성 검증 |
| 화면 인식 | 대상 창 캡처 + 로컬 OCR | UIA·텍스트 복사가 불가능한 부분의 보완 |
| 로컬 저장 | SQLite 기반 관계 데이터·검색 인덱스 | 암호화 배포 구성은 P0에서 결정 |
| 의미 검색 | 로컬 임베딩 + 벡터 인덱스 | 한국어 검색 평가로 모델·인덱스 선택 |
| 로컬 생성 AI | Ollama의 로컬 API | 대상 PC에서 모델 선정, 클라우드 기능 비활성화 |
| 일정 처리 | 영속 작업 큐·알림 서비스 | 앱 재시작·절전 복구 지원 |
| 첨부 처리 | 다운로드 관리자·형식별 추출 작업자 | 파일 형식과 크기에 따른 제한 적용 |

계층과 의존성:

1. 화면 계층: 패널, 검색, 업무 대시보드, 편집기, 수신자 선택.
2. 업무 계층: 수집, 업무화, 검색, 그룹, 초안, 예약, 파일 관리.
3. 연동 계층: 온톡 어댑터, 로컬 AI, 파일 추출, 알림.
4. 저장 계층: 프로필별 데이터, 검색 인덱스, 파일 저장소, 실행 기록.

업무 계층은 온톡의 버튼 좌표나 창 이름에 직접 의존하지 않는다. 온톡 업데이트 시 연동 계층을 변경한다. 어댑터는 현재 사용 가능한 기능 목록을 제공하여 지원하지 않는 기능을 UI에서 명확히 표시한다.

로컬 HTML·스크립트·폰트 자산을 패키지에 포함한다. 편집기는 외부 CDN에 의존하지 않는다. WebView2의 외부 이동과 파일 접근을 제한하고, 앱과 편집기의 메시지 규격을 검증한다.

## 5. 온톡 연동 규칙

### 5.1 자동화 우선순위

공식 지원 인터페이스 또는 내보내기 → UI Automation → 지원되는 복사 기능 → 대상 창 OCR → 제한된 키보드·마우스 입력 순서로 선택한다.

고정 좌표를 기본 식별 수단으로 사용하지 않는다. 창·역할·레이블·부모 관계·수신자 정보를 조합한다. 키보드·마우스 입력이 필요한 작업은 하나씩 수행하고, 사용자의 포커스 전환이나 대상 변경을 감지하면 중단한다.

클립보드를 사용하면 기존 내용을 가능한 범위에서 보존한다. 복구 시점에 사용자가 새 내용을 복사했다면 그 내용을 덮어쓰지 않는다.

### 5.2 연결 상태

미실행 → 로그인 대기 → 계정 확인 → 연결됨 → 연결 불확실/연결 해제.

계정이 확정되기 전에는 업무 데이터 수집·초안 입력·그룹 수정·예약 등록을 수행하지 않는다. 로그아웃이나 다른 계정으로 전환되면 진행 중 연동 작업의 계정 토큰을 무효화한다.

### 5.3 수집 모드

- 기본: 사용자가 연 쪽지를 수집·분석.
- 선택 수집: 사용자가 선택한 쪽지 목록을 순서대로 수집.
- 과거 기록 수집: 지원되는 내보내기 또는 검증된 UI 순회, 중단·재개 지점 기록.

목록 순회 중 쪽지를 열면 읽음 상태가 바뀔 수 있다. 자동 수집을 켜기 전에 이 동작을 실제 검증하고 사용자에게 알려야 한다. 사용자의 작업 중 대량 순회가 창을 계속 전환하지 않도록 별도 실행 흐름으로 제공한다.

고유번호가 있으면 이를 우선 키로 사용한다. 없으면 프로필·발신자·수신자·원문 시각·본문·첨부 정보로 중복 후보를 찾되, 동일 본문의 반복 전송을 자동으로 하나로 지우지 않는다. 수집 시각과 발송/수신 시각은 별도로 기록한다.

### 5.4 발송과 예약 상태

초안 → 검토 완료 → 온톡 반영 중 → 전송/예약 등록 시도 → 결과 확인.

확인 결과는 발송 확인, 예약 등록 확인, 명확한 실패, 결과 미확인으로 나눈다. 예약 등록은 실제 발송 완료와 다르다.

발송 직전 수신자·본문·첨부·예약 시각을 다시 읽어 초안 스냅샷과 비교한다. 바이트 제한은 확인된 온톡 규칙으로 계산하고, 입력 후 온톡 표시와 재확인한다. 변수가 채워지지 않은 템플릿은 발송 대상으로 넘기지 않는다.

전송/예약 동작 전에 실행 기록을 저장한다. 앱 종료·타임아웃 등으로 결과가 불확실하면 자동 재전송하거나 재등록하지 않는다. 보낸 쪽지·예약 목록 등 확인 가능한 근거로 상태를 복구한다. 화면제어만으로 정확히 한 번 전달을 보장한다고 표현하지 않는다.

온톡 예약 기능을 사용한 항목은 로컬 스케줄러가 같은 시각에 다시 전송하지 않는다. 로컬 스케줄러는 업무 알림과 예약 상태 점검을 담당한다. 네이티브 예약의 PC 종료 후 동작은 시험 결과로 안내한다.

날짜에는 원문 표현, 해석된 값, 기준 시각, 시간대, 확정 여부를 저장한다. 원문에 연도가 없거나 상대 날짜가 모호하면 검토 대상으로 둔다. 일정의 내부 시각과 표시 시간대는 분리하고 기본 표시 시간대는 Asia/Seoul로 한다.

## 7. 첨부파일과 보존

파일 상태: 발견 → 다운로드 대기 → 다운로드 중 → 저장 검증 → 내용 추출 → 검색 가능. 실패·접근 불가·암호 필요 상태는 각각 표시한다.

다운로드 종료와 실제 파일 존재·크기 등을 확인한 뒤 확보 완료로 표시한다. 내용 해시가 같아도 각 쪽지의 파일 연결 기록은 유지한다. 같은 이름에 다른 내용이면 별개 버전이다.

PDF·DOCX·XLSX·PPTX·텍스트·이미지 등은 형식별 추출기를 단계적으로 검증한다. HWP/HWPX는 보관·열기·업무 연결을 지원하고, 본문 추출은 대상 환경의 파서·변환 가능성을 확인해 범위를 확정한다. 이미지의 OCR 결과에는 인식 결과임을 표시한다. 파일 내용 추출 실패가 원본 보관을 막지 않게 한다.

매크로나 첨부 파일의 실행 코드에 의존해 내용을 읽지 않는다. 추출 작업에는 용량·시간 제한을 두고 원본은 변경하지 않는다. 첨부 내용은 AI 입력 자료로만 사용한다.

원본 만료 안내, 온톡 보관 상태, 로컬 파일 확보 상태를 따로 표시한다. 화면의 '7일' 안내만으로 정확한 만료 시각을 확정하지 않는다. 서버 기준이 확인되기 전에는 원문 안내와 추정 여부를 함께 표시한다.

보존 기간과 삭제 기능은 원문·파일·검색 인덱스·임베딩·AI 캐시·백업까지 고려한다. 단순한 쪽지 삭제나 보관 여부와 사이드카의 사본 보존은 별개로 다룬다.

## 8. 로컬 AI 설계

### 8.1 역할

- 쪽지 요약과 근거 문장 추출.
- 업무 후보·대상·기한·요청사항·미확인 사항 구조화.
- 자연어를 사람/쪽지 검색 조건으로 변환.
- 임베딩 기반 의미 검색과 검색 결과 요약.
- 답장 초안·문체 수정·길이 축약.

AI는 발송·그룹 변경·파일 삭제를 직접 호출하지 않는다. 사용자 요청을 바탕으로 정해진 형식의 제안을 만들고, 업무 코드가 필드와 대상의 유효성을 검사한다. 쪽지·첨부·조직도 문자열 안의 실행 지시는 신뢰하지 않는다.

### 8.2 분석 결과 형식

분석 결과에는 summary, actions, audience, dates, attachments, uncertainties, evidence를 둔다. 각 업무 후보는 원문 근거 위치와 원문에 명시된 값인지 추론인지 기록한다. 스키마 일치만으로 사실이 맞다고 판정하지 않는다.

분석은 쪽지별 원문 버전에 묶는다. 사용자가 편집한 업무를 AI 재분석 결과가 자동 덮어쓰지 않는다. 발신 시각·수신 시각·마감 시각을 구별하고, 명시되지 않은 기한은 null로 둔다.

### 8.3 실행 방식

임베딩 모델과 생성 모델을 분리한다. 업무 PC의 RAM·GPU·저장 공간과 한국어 평가 결과로 모델을 선택한다. 설치 용량·라이선스·컨텍스트 길이·응답 속도를 함께 기록한다.

클라우드 모델과 웹 검색 기능을 비활성화하고 로컬 API를 루프백에 제한한다. 모델과 의존 자산을 준비한 뒤 네트워크 차단 상태에서 기능을 검증한다. 로컬 실행 설정만으로 자동 업데이트나 모델 다운로드까지 모든 통신이 사라졌다고 가정하지 않는다.

AI가 실행되지 않아도 정확 검색·수동 업무 등록·템플릿·파일 연결을 사용할 수 있게 한다. 사용자가 취소하거나 다른 쪽지로 이동하면 불필요한 분석을 취소한다.

## 9. 저장·배포 운영 설계

기본 배포 대상은 검증한 Windows 업무 PC다. .NET·WebView2·모델·OCR 언어 자산의 버전을 고정하고 설치 목록을 제공한다. 연결망이 제한된 환경을 위해 오프라인 설치 경로를 준비한다. 조직의 배포 방식에 따라 서명된 설치 프로그램 또는 허용된 패키지 방식을 선택한다.

저장 암호화 방식은 P0에서 배포 가능성과 검색 성능을 검증해 결정한다. 일반 SQLite가 자동으로 암호화된다고 가정하지 않는다. 원문뿐 아니라 전문 검색 인덱스·벡터·첨부파일·임시파일도 보호 대상에 포함한다. 키 보관·백업·복구·계정 이동 절차를 함께 설계한다.

진단 로그에는 원문 전체·연락처 전체·비밀번호를 기록하지 않는다. UI 진단 자료는 필요한 구조만 수집하고 개인 정보를 가린다. 사용자에게 수집 중/일시정지/연결 해제 상태와 수집 범위를 표시한다.

업데이트 전 저장소를 백업하고 마이그레이션 버전을 기록한다. 실패 시 이전 데이터로 복구 가능한 절차를 갖춘다. 온톡 업데이트로 어댑터 검증이 실패하면 연동을 중지하고 저장된 업무와 파일은 계속 열람하게 한다.

## 10. 단계별 구현 계획

추정 전제: 숙련 개발자 1명, 주 5일, 테스트 가능한 온톡 계정·PC와 송수신 상대 확보, 과도한 배포 제약 없음. 아래 기간은 개발 계획용 추정이며 실측이 아니다. P0 결과로 다시 산정한다.

| 단계 | 기간 | 주요 산출물 | 다음 단계로 넘어갈 기준 |
|---|---|---|---|
| P0 연동 기술검증 | 1주 | UI 구조·기능별 접근 방식, 서식·바이트·예약·파일 시험 결과, 모델/저장/배포 후보 | 지원 가능한 경로와 제한을 기능별로 확정 |
| P1 기본 앱 | 1주 | 프로필·연결 상태·패널·저장소·어댑터 인터페이스·진단 | 로그인/로그아웃/계정/창 전환 시 상태와 자료가 일치 |
| P2 읽기·업무·파일·AI | 2주 | 현재 쪽지 수집, 근거 있는 분석, 업무 선택, 알림, 파일 확보 | 한 쪽지에서 선택한 업무·원문·파일이 연결되어 재시작 후 복구 |
| P3 통합검색 | 1주 | 정확 검색·필터·의미 검색·수집 범위·출처 표시 | 이름/짧은 한국어/날짜/의미 질의 평가 통과 |
| P4 조직도·그룹·편집기 | 2주 | 사람 검색, 그룹, 템플릿, 서식 편집, 실제 전송 표현 | 수신자 식별과 서식 변환·초안 보존 검증 통과 |
| P5 발송·예약 연동 | 1~2주 | 온톡 반영, 네이티브 예약 연결, 상태 확인·복구 | 오수신자 입력·불확실 결과 재전송 방지 시험 통과 |
| P6 실사용·배포 검증 | 1~2주 | 시범 사용, 오프라인 설치, 업데이트·백업·복구, 운영 안내 | 목표 환경에서 기능·성능·복구 기준 충족 |

기본 개발 9~11주, 온톡 호환성·한국어 AI·배포 대응 예비 2~3주를 두어 총 11~14주를 초기 계획 범위로 본다. 대규모 과거 기록 이관, 복잡한 HWP 변환, 온톡 실제 그룹 편집 실패에 대한 대체 구현은 재산정 항목이다.

P2 종료 시 읽기·업무화 중심의 첫 사용 가능한 버전을 제공한다. 사용자가 원하는 전체 기능의 완료는 P5 및 P6 검증 후로 판단한다.

### 10.1 P0의 구체적인 시험

1. 실행 중 프로세스·창·UIA 요소를 필요한 범위에서 조사하고 개인정보를 가린 결과를 저장한다.
2. 같은 쪽지를 UIA·복사·OCR로 읽어 원문·발신자·시각·첨부의 일치 정도를 비교한다.
3. 목록 재조회·스크롤·창 재열기·재로그인 후 동일 쪽지 식별을 확인한다.
4. 조직도에서 이름·부서·동명이인을 구분하고 수신자 추가/제거를 확인한다.
5. 별도 테스트 송수신 환경에서 글꼴·굵게·색상·목록·이모지의 수신 결과를 확인한다.
6. 한글·ASCII·이모지·줄바꿈·인용문과 4000바이트 경계의 계산을 확인한다.
7. 첨부 다운로드·중복 이름·저장 실패·재열기를 확인한다.
8. 네이티브 예약 등록·조회·수정·취소·재접속을 확인한다. PC 종료 후 발송은 실제 예약 시험으로 판단한다.
9. 로컬 AI의 한국어 업무 추출과 임베딩 검색을 작은 익명 평가셋으로 비교한다.

테스트 발송은 정해진 테스트 수신자·내용·예약 시각으로만 수행한다. 이 문서 작성 단계에서는 실제 발송이나 로그인 조작을 수행하지 않았다.

### 10.2 기술검증 결과에 따른 분기

| 결과 | 구현 방향 |
|---|---|
| 본문·사람·입력창을 구조적으로 읽고 조작 가능 | 통합 사이드카 구현 진행 |
| 본문은 읽히지만 쓰기/수신자/예약 확인이 제한됨 | 읽기·검색·업무화 구현, 발송은 초안 전달과 사용자 조작 연결 |
| OCR 또는 수동 복사만 가능 | 선택 가져오기 중심으로 시작, 자동 수집·발송은 지원 범위에서 명시적으로 제외 |
| 본문·화면·복사가 모두 차단됨 | 자동 연동은 중단 판정, 공식 연동 또는 사용자가 입력한 자료 기반 범위로 재설계 |
| 서식이 수신 결과에서 사라짐 | 로컬 서식 편집 + 텍스트 전송 미리보기, 서식 첨부 방식 검토 |
| 네이티브 예약의 결과를 확인할 수 없음 | 예약 화면 연결까지 제공, 등록 완료를 임의로 표시하지 않음 |

제약이 발생한 기능을 완료로 처리하지 않는다. 기능별 지원·부분 지원·미지원 상태와 근거를 결과 문서에 남긴다.

## 11. 검증 및 완료 기준

다음 수치는 초기 수용 목표이며 검증 결과가 아니다. P0에서 대상 PC·표본 수를 확정한 뒤 조정한다.

| 영역 | 수용 기준 |
|---|---|
| 계정 격리 | 로그인·로그아웃·기관/계정 전환 시험에서 다른 프로필 자료나 초안 혼합 0건 |
| 쪽지 연결 | 대표 표본 50건에서 발신자·시각·본문·첨부의 연결 오류 0건; 미확인 값을 숨기지 않음 |
| 업무 추출 | 익명 표본 50건 이상으로 명시적 업무·기한의 정확도/누락률 측정, 존재하지 않는 확정 기한 0건 목표 |
| 검색 | 짧은 이름·부서·문서번호·날짜를 포함한 정답 질의셋 검증, 의미 질의 상위 5개 적중률 90% 목표 |
| 파일 | 원본 보존, 동일 이름 다른 내용 분리, 다운로드 중단과 추출 실패 표시, 재시작 후 연결 복구 |
| 편집 | 한글 IME, 실행취소, 초안 자동저장, 이모지, 인용문, 4000바이트 경계, 수신 서식 확인 |
| 발송 | 수신자·내용·첨부 불일치 시 실행 중단, 불확실 결과의 자동 재전송 0건, 발송과 예약 등록 구분 |
| 일정 | 재시작·절전 복귀·시간 변경·완료 처리 후 알림 중복과 유실 검증 |
| 화면 | 100/125/150/200% 배율, 창 이동·다중 모니터·팝업·다중 쪽지·포커스 변경 시험 |
| 오프라인 | 준비된 모델과 자산으로 네트워크 차단 상태에서 읽기·검색·AI·편집 사용 가능 |
| 성능 | 확정할 기준 PC에서 1만 건 기준 문자 검색 1초 내, AI 진행 표시·취소 즉시 반응 목표; AI 완료시간은 실측 보고 |
| 복구 | 마이그레이션·백업 복원, 어댑터 오류, 다운로드 중단, 발송 직후 앱 종료 시 상태 복구 |

단위 테스트는 날짜 해석 결과 검증, 상태 전이, 계정 범위, 중복 후보 처리, 바이트 규칙, 텍스트 변환에 집중한다. 통합 테스트는 저장소·검색·추출기·로컬 AI의 연결을 확인한다. 실제 온톡 호환성은 테스트 계정과 상대를 사용하는 수동·자동 시나리오로 검증한다.

AI 평가에서는 모델이 만든 답을 정답으로 재사용하지 않는다. 원문에서 사람이 확인한 정답을 기준으로 측정한다. 표본에서 오류 0건이라고 실제 환경의 무오류를 보장하지 않는다.

## 12. 구현 산출물 구조

예정 구조:

```text
src/
  OnTalk.Sidecar.App/             WPF 앱·패널·설정
  OnTalk.Sidecar.Core/            업무·초안·검색·예약 규칙
  OnTalk.Sidecar.Automation/      온톡 어댑터와 UI 접근 작업자
  OnTalk.Sidecar.Storage/         프로필·저장소·검색·마이그레이션
  OnTalk.Sidecar.AI/              로컬 모델·추출 스키마·근거 연결
  OnTalk.Sidecar.Attachments/     파일 확보·추출·버전 관리
  OnTalk.Sidecar.Editor/          오프라인 편집기 자산
tests/
  Core.Tests/
  Integration.Tests/
  CompatibilityScenarios/
tools/
  Diagnostics/                   UI 구조·호환성 진단
docs/
  design-and-implementation-plan.md
  feasibility-results.md         P0 후 작성
  compatibility-matrix.md        대상 온톡/Windows/모델 버전별 지원
  pilot-results.md               실사용 검증 결과
```

첫 구현 작업은 연동 진단 도구와 본문 수집 시험이다. 제품 전체를 먼저 작성한 뒤 화면제어가 가능한지 확인하는 순서를 피한다. 진단 결과로 어댑터 계약과 실제 지원 범위를 고정하고 기능 구현에 들어간다.
