# 설계 및 구현 계획서 검토

- 작성일: 2026-10-03, Asia/Seoul
- 검토 대상: [design-and-implementation-plan.md](design-and-implementation-plan.md)
- 검토 방법: 계획서 정독 + 이 PC에 설치된 온톡의 실행 파일·설치 폴더·프로세스·UI 접근성 직접 확인
- 개인정보 처리: 쪽지·대화 원문, 로컬 DB 내용, 로그 내용은 열람하지 않았다. 접근성 조사는 요소 개수만 집계하고 이름·본문은 출력하지 않았다.

## 총평

계획서는 확인되지 않은 사항을 미확인으로 남기고, 발송 상태를 단계별로 관리하며, 결과가 불확실하면 다시 보내지 않고, AI가 직접 실행하지 못하게 하는 등 신중하게 작성되었다. 다만 앱을 직접 확인하지 않은 상태에서 작성되어 **핵심 전제인 "UI Automation으로 읽는다"가 기본 상태에서는 성립하지 않는다.** 연동 방식의 우선순위와 P0 시험 순서를 고쳐야 한다.

## 2. 주요 문제와 보완점

중요한 순서로 정리했다.

### ① 연동 방식의 우선순위를 다시 정해야 한다

Chromium 78에는 자체 UIA 제공자가 없고, 접근성 트리는 스크린리더를 감지했을 때나 실행 옵션을 줬을 때만 켜진다. P0에서 다음 선택지를 차례로 시험한다.

| 순서 | 방식 | 장점 | 위험 |
|---|---|---|---|
| 1 | 온톡을 `--force-renderer-accessibility` 옵션으로 실행(바로가기 수정) | 계획서의 UIA 설계를 그대로 쓸 수 있다 | 성능 저하 가능성. 가상 스크롤 목록은 화면에 보이는 항목만 잡힌다 |
| 2 | 대상 창 캡처 + 로컬 OCR | 앱을 바꾸지 않는다 | 정확도가 떨어지고 입력(쓰기)은 할 수 없다 |
| 3 | `--remote-debugging-port`(CDP)로 화면 구조를 직접 읽기 | 가장 정확하고 식별자까지 얻을 수 있다 | 이 앱은 `node-integration`이 켜져 있어서 **포트에 접속하는 로컬 프로세스는 사용자 권한으로 임의 코드를 실행할 수 있다.** 보안 승인 없이 사용 금지 |
| 4 | `user.db` 읽기 전용 열람 | 과거 기록 수집과 7일 삭제 문제를 한 번에 풀 수 있다 | 암호화 여부·스키마 미확인. 개인정보·보안 승인 필요 |

`app.asar` 수정이나 코드 주입은 업데이트 때 덮어써지고 앱 무결성을 깨므로 제외한다.

5.1절의 우선순위를 다음과 같이 고칠 것을 제안한다.

> 공식 지원 인터페이스 → (승인 시) 로컬 저장소 읽기 전용 열람 → 접근성 활성화 후 UI Automation → 대상 창 OCR → 지원되는 복사 기능 → 제한된 키보드·마우스 입력. CDP는 보안 승인을 받은 경우에만 별도 검토한다.

### ② P0에 조직 승인 절차가 빠져 있다

부산광역시 업무 PC에서 메신저 원문을 로컬에 별도 저장하고, AI 모델을 반입하고, 화면을 캡처하는 일은 정보보안 담당 부서의 승인 대상이다. 특히 "쪽지 7일 후 삭제"는 기관 정책일 수 있다. 사본을 계속 보관하는 기능([7절](design-and-implementation-plan.md#7-첨부파일과-보존))은 정책과 충돌할 수 있으므로 구현 전에 확인한다. 실행 중인 보안 에이전트가 입력 주입·캡처·후킹을 막는지도 함께 확인한다.

### ③ 입력창 값 반영 방식에 함정이 있다

SPA 프레임워크로 만든 입력창은 UIA `ValuePattern.SetValue`로 값을 바꿔도 앱 내부 상태가 갱신되지 않을 수 있다. 화면에는 글이 보이는데 실제로는 빈 내용이 발송될 수 있다. [5.4절](design-and-implementation-plan.md#54-발송과-예약-상태)의 "발송 직전 재확인"에 더해, **붙여넣기·키 입력처럼 실제 사용자 입력과 같은 경로만 사용**하고 입력 후 온톡의 바이트 표시가 바뀌었는지로 반영 여부를 확인하도록 명시한다.

### ④ P0 시험 일부는 코드 확인으로 대체할 수 있다

4000바이트 계산 기준(UTF-8인지 EUC-KR인지), 서식 지원 여부, 예약 전송 동작은 배포된 소스맵에서 확인할 수 있다. 실제 발송 시험 횟수가 줄어든다. 다만 업체 소프트웨어를 분석하는 일이므로 사용 허락 범위를 먼저 확인한다.

### ⑤ 새 쪽지 감지 방식이 빠져 있다

쪽지창이 별도 창이므로 폴링보다 `SetWinEventHook`의 창 생성 이벤트(`EVENT_OBJECT_CREATE`/`EVENT_OBJECT_SHOW`)를 받는 방식이 가볍고 정확하다. [3.2절](design-and-implementation-plan.md#32-읽기-패널)의 창 따라다니기도 `EVENT_OBJECT_LOCATIONCHANGE`를 사용한다. 온톡 창은 자체 제목 표시줄을 쓰는 프레임 없는 창이므로 배율·다중 모니터 시험에 포함한다.

### ⑥ 로컬 AI 설계를 대상 PC 사양에 맞춰야 한다

전용 GPU가 없으므로 7B 이상 생성 모델은 요약 한 건에 수십 초가 걸릴 수 있다. 임베딩은 한국어에 강한 다국어 모델(예: bge-m3), 생성은 3~4B급 모델로 시작하고, 각 모델의 라이선스가 공공기관 업무 사용을 허용하는지 확인한다. AI 없이도 기본 기능이 동작하게 한 계획서의 원칙([8.3절](design-and-implementation-plan.md#83-실행-방식))은 유지한다.

### ⑦ 일정이 낙관적이다

11~14주에 편집기(WebView2+Tiptap, 한글 입력 검증), 온톡 그룹 반영, 예약 자동화, 첨부 추출까지 모두 넣으면 개발자 1명으로는 빠듯하다. 첫 버전에서는 R06~R08(편집기·발송·예약)을 **"초안을 클립보드로 넘기고 사용자가 직접 보내기"** 수준으로 낮추고, 읽기 패널·업무화·통합검색(R02~R04)을 먼저 완성할 것을 권한다.

### ⑧ 계정 식별의 보조 근거

저장 폴더 이름이 로그인 ID이고 활성 계정의 DB 수정 시각이 갱신되므로, 현재 활성 계정을 판단하는 보조 근거로 쓸 수 있다([3.1절](design-and-implementation-plan.md#31-연결과-로그인)). 단독 근거로는 쓰지 않는다.

## 3. 계획서의 유지할 강점

- 기능별로 지원·부분 지원·미지원을 구분하고 근거를 남기는 원칙([10.2절](design-and-implementation-plan.md#102-기술검증-결과에-따른-분기)).
- 발송과 예약 등록을 구분하고, 결과가 불확실하면 자동으로 다시 보내지 않는 상태 설계.
- 쪽지·첨부·조직도 문자열 안의 지시를 AI가 따르지 않게 한 규칙.
- 계정별 저장소와 검색 범위의 분리.
- 제품 전체를 먼저 만들지 않고 진단 도구부터 만드는 순서([12절](design-and-implementation-plan.md#12-구현-산출물-구조)).

## 4. 권장하는 P0 재구성 (1주)

1. **보안·정책 확인**: 원문 로컬 보관, AI 모델 반입, 온톡 실행 옵션 변경, CDP 사용 가능 여부, 소스맵 분석 허용 범위.
2. **접근성 활성화 시험**: `--force-renderer-accessibility`로 온톡을 실행한 뒤 쪽지창의 본문·발신자·시각·첨부가 UIA로 읽히는지, 목록 가상화 범위와 성능 영향을 확인한다.
3. 2가 실패하면 OCR 정확도를 측정하고, 승인된 경우에 한해 CDP나 로컬 DB 읽기를 검토한다.
4. **입력 시험**: 붙여넣기 방식으로 넣은 내용이 앱 상태에 실제로 반영되는지, 바이트 계산 규칙이 무엇인지 확인한다.
5. 결과에 따라 10.2절의 분기표대로 범위를 확정하고 `feasibility-results.md`에 기록한다.

## 5. 이번 검토에서 하지 못한 것

- `user.db`의 암호화 여부와 스키마 확인: 개인정보 보호 규칙에 따라 열람하지 않았다. 연동 수단으로 검토하려면 사용자가 직접 확인하거나 승인 범위를 정해야 한다.
- `--force-renderer-accessibility` 활성화 시험: 사용 중인 온톡을 재시작해야 해서 수행하지 않았다.
- 소스맵 기반 코드 확인: 사용 허락 범위 확인 전이므로 수행하지 않았다.
