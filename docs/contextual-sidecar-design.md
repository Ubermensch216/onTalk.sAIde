# 온톡 메뉴·작업별 사이드카 분석 및 설계

- 작성일: 2026-10-04, Asia/Seoul
- 상태: 1차 문맥 일치·쪽지 읽기/작성 분리, 2차 친구·조직도 관찰 목록·선택·연락 준비에 이어, 3차 대화 원문 선택·정리·답변·근거 업무, 자연어 검색어 제안과 사람/쪽지의 명시적 연결을 구현했다. 방·사람의 고유 ID, 대화 입력 반영과 실제 제품 감시/파서의 수용 검증은 남아 있다. 실제 변경과 확인 범위는 [1차](contextual-sidecar-implementation.md), [2차](contextual-sidecar-phase2.md), [3차 기록](contextual-sidecar-phase3.md)에 있다. 아래는 전체 목표 설계이며 모든 항목이 구현되었다는 뜻은 아니다.
- 대상: 메인 화면의 **친구·조직도·대화·쪽지**, 여기서 이어지는 대화창·쪽지 읽기·쪽지 작성창.
- 제외: **사용자 검색·알리미 메뉴**의 전용 사이드카 설계. 기존 쪽지 작성 과정의 수신자 추가 도구는 유지한다.
- 목표: 사용자가 지금 처리하는 작업에 맞춰 사이드카의 제목·내용·도구·주요 행동이 함께 바뀐다.

## 1. 분석 근거와 확인 범위

| 근거 | 이번 설계에서 사용하는 사실 | 확인 수준 |
|---|---|---|
| 2026-10-04 실제 온톡 메인 화면 | 친구의 나의 그룹·그룹 만들기·그룹/사람 선택, 온라인 상태, 사람 상세 정보; 조직도의 내 기관·타 기관 조회, 부서 트리·사람 선택; 이름·전화번호·부서·메일·담당업무 검색, 모두 보기 선택 | 이번 작업에서 친구·조직도 화면 확인. 상세 메뉴의 실행 결과는 미확인 |
| [기존 설계서 1.1절](design-and-implementation-plan.md#11-화면에서-확인한-사실) | 받은·보낸·보관 쪽지 목록, 받은 쪽지의 답장·전체답장·전달, 작성창의 인용·수신자·첨부·예약·SMS | 기존 화면 조사 기록. 이번 작업에서 재검증하지 않음 |
| [연동 검증 결과](feasibility-results.md) | 메인·대화·쪽지 페이지 경로, MSAA 읽기, 받은 쪽지·작성창·수신자 추가·예약 연동 | 과거 검증 기록. 대화 메시지·참여자 식별·입력 연동은 검증되지 않음 |
| 현재 `PanelWindow`, `OnTalkDock`, `NoteWatcher`, `NoteWindowParser` | 창 부착과 표시 내용 선택의 분리, 쪽지 위주의 화면·파서 | 소스 코드 확인 |

실제 화면 확인 중 온톡이 로그인 화면으로 전환되어 대화 목록·대화창·쪽지 화면의 추가 탐색을 종료했다. 따라서 아래의 대화 기능은 **업무 메신저 사용 작업을 바탕으로 한 제안**이며 온톡에 이미 있는 기능이라고 주장하지 않는다. 문서와 미리보기의 사람·쪽지·대화 사례는 가상 예시이고 실제 개인정보를 옮기지 않았다.

기존 문서에는 과거 버전의 미확인 기록과 후속 검증 결과가 함께 남아 있다. 구현 유무는 현재 코드를 기준으로, 실제 동작의 확인 수준은 가장 나중의 해당 검증 기록을 기준으로 읽는다. 이 문서는 메뉴별 문맥·화면 설계를 구체화하며 기존 계정 격리·보관·반영 확인·전송 규칙을 유지한다.

## 2. 현재 고정 화면이 생기는 이유

1. `OnTalkDock.Poll()`은 마지막으로 사용한 온톡 창을 부착 대상으로 고른다. 창 종류나 메인 화면의 메뉴는 해석하지 않는다.
2. `NoteWatcher`는 쪽지 페이지만 수집하고 다른 페이지를 `_notNotePages`에 넣어 재검사를 생략한다. 메인 메뉴 변경이나 같은 창에서 페이지가 바뀌는 경우를 다루는 문맥 감시기가 없다.
3. `PanelWindow.Apply()`는 받은 쪽지 중 전경 창 → 이전 `_attached` → 첫 받은 쪽지 순서로 표시 대상을 고른다. `_dockedTo`와 같은 대상인지 확인하지 않는다.
4. `PanelWindow.xaml`의 내용은 받은 쪽지 머리 정보와 ‘정리·원문’ 탭으로 고정되어 있다. 작성 지원은 별도의 `ComposeWindow`를 열어야 한다.
5. `NoteWindowKind`는 `Unknown / Received / Compose`만 구분한다. 새 쪽지·답장·전체답장·전달의 목적 차이가 UI 정책으로 연결되지 않는다.
6. 초안은 `new` 또는 `note:{noteId}` 슬롯을 쓴다. 여러 새 쪽지, 같은 원문에 대한 답장·전달, 여러 대화방의 초안을 동시에 구분할 수 있는 구조가 아니다.

결과적으로 **사이드카가 붙은 창과 사이드카가 설명하는 대상이 다를 수 있다.** 예를 들어 받은 쪽지 A가 열린 상태에서 친구 메뉴로 돌아오면, 부착은 메인 창을 따라가지만 내용은 A를 계속 선택할 수 있다. 작성창 옆에서도 읽기 화면이 남을 수 있다.

해결 단위는 창 종류 하나가 아니라 **현재 창 + 활성 메뉴 + 선택 대상 + 작업 상태**다. 사이드카가 받은 쪽지 저장소를 갖고 있는 것과, 지금 받은 쪽지를 보여 주어야 하는 것은 별개의 판단이다.

## 3. 메뉴별 목적과 사이드카 역할

| 메뉴/상황 | 온톡에서 하는 일 | 사이드카의 역할 | 기본 표시 | 가장 중요한 행동 |
|---|---|---|---|---|
| 친구, 선택 없음 | 자주 연락하는 사람·개인 그룹 찾기 | 연락할 대상·그룹 준비 | 사람/그룹을 선택하는 안내, 로컬 그룹 도구 | 그룹 준비 |
| 친구, 사람 선택 | 사람 확인·연락 시작 | 그 사람과의 업무 맥락 확인 | 신원·담당업무, 연결된 미완료 업무, 관련 보관 자료 | 선택한 사람에게 보낼 내용 준비 |
| 친구, 그룹/여러 사람 선택 | 여러 사람에게 연락 | 구성원·목적 점검 | 선택 구성원, 동명이인·중복 확인, 그룹별 문구 | 수신자 묶음 준비 |
| 조직도, 선택 없음 | 기관·부서를 따라 담당자 탐색 | 담당업무로 후보 좁히기 | 자연어 담당자 탐색, 검색 범위 | 담당자 후보 찾기 |
| 조직도, 부서 선택 | 부서 구성원·역할 확인 | 필요한 역할과 후보 비교 | 선택 부서, 확인한 담당업무·후보, 선택 범위 | 연락 대상 구성 |
| 조직도, 사람/여러 사람 선택 | 담당자 확인·수신자 구성 | 대상 적합성과 신원 확인 | 부서·직급·담당업무, 선택 이유, 수신자 묶음 | 쪽지 작성으로 이어가기 |
| 대화 목록 | 진행 중인 대화방 찾기 | 참여할 대화의 맥락 복구 | 선택 방의 최근 확보 내용·열린 업무 | 대화 준비 |
| 대화창, 읽기/선택 메시지 | 흐름 파악·질문 확인 | 놓친 내용·결정·해야 할 일 정리 | 요약, 결정/검토 구분, 미답변 질문·업무 후보 | 읽은 범위 정리 |
| 대화창, 답변 작성 | 짧은 답변·질문·공유 작성 | 대화 맥락에 맞는 답변 작성 | 답변 의도, 초안·문장 다듬기, 근거 확인 | 검토한 초안을 입력창에 반영 |
| 쪽지 목록 | 받은·보낸·보관 쪽지 찾아보기 | 보관 자료에서 필요한 쪽지·업무 찾기 | 현재 쪽지함, 보관 범위, 선택 쪽지/관련 업무 | 읽을 쪽지 찾기 |
| 받은 쪽지 읽기 | 내용 이해·요청 확인 | 읽기·이해 지원 | 핵심 요약, 요청·기한·근거, 확인할 점, 첨부 상태 | 원문 확인 또는 업무 후보 등록 |
| 보낸/보관 쪽지 읽기 | 과거 내용 확인 | 내용·연결 업무 조회 | 내용 요약·원문·연결 업무 | 관련 자료 확인 |
| 새 쪽지 작성 | 새 요청·공지·문의 작성 | 내용 구성·에디팅 지원 | 작성 목적, 핵심 사실, 초안·템플릿, 최종 점검 | 초안 반영 |
| 답장 작성 | 발신자 요청에 응답 | 요청별 응답 작성 | 원문의 질문·요청, 응답 누락, 초안·인용 | 응답 초안 반영 |
| 전체답장 작성 | 여러 수신자에게 함께 응답 | 공동 응답·공유 범위 점검 | 답장 기능 + 실제 전체 수신자 확인 | 수신자·내용 확인 후 반영 |
| 전달 작성 | 다른 사람에게 원문 공유 | 전달 목적·설명 작성 | 전달받는 사람, 소개 문장, 원문·첨부 포함 상태 | 전달 설명 반영 |

공통 관리·보관 검색·업무 목록은 유지하되 상단의 공통 도구에 둔다. 각 문맥의 본문에는 그 작업에 필요한 내용만 우선 배치한다. 친구·조직도에서 받은 쪽지 요약을 기본 화면으로 보여 주지 않는다.

## 4. 친구: ‘사람과 관계를 기준으로 연락 준비’

### 4.1 기본 기능

- **선택한 사람 확인**: 이름·기관·부서·직급·화면에 공개된 담당업무를 묶어 보여 준다. 온톡의 현재 표시와 확인 시점을 함께 남긴다.
- **그 사람과 관련된 업무**: 명확히 연결한 미완료 업무와 보관 쪽지를 보여 준다. 이름 문자열만 같은 자료는 ‘관련 후보’로 분리한다.
- **연락 준비**: 문의·진행 확인·자료 요청·감사 등 의도를 고르면 초안 도구로 이어진다. 온라인 상태는 연락 시 참고 정보이며 응답 가능성을 단정하지 않는다.
- **그룹 준비**: 선택한 사람을 사이드카의 로컬 그룹으로 묶고 구성원·중복·확인 수준을 표시한다. 온톡 ‘나의 그룹’과는 구분한다.
- **그룹별 문구**: 자주 쓰는 대상과 문구를 연결한다. 실제 전송 대상은 작성창에서 다시 확인한다.

### 4.2 선택에 따른 변화

선택이 없으면 사람별 이력을 보여 주지 않는다. 한 명이면 ‘사람 정보 → 관련 업무 → 연락 준비’, 여러 명이면 ‘구성원 → 중복·신원 확인 → 일괄 연락 준비’, 그룹이면 ‘그룹 구성원 → 관련 업무 → 그룹 문구’가 우선이다.

온톡에서 선택을 읽을 수 없으면 “온톡 선택을 확인하지 못했습니다”와 수동 대상 선택을 제공한다. 수동 지정은 사이드카 문맥만 바꾸며 온톡의 선택이 변경되었다고 표시하지 않는다. 수신자 자동 반영은 별도 검증이 통과했을 때만 제공한다.

## 5. 조직도: ‘업무에 맞는 담당자와 연락 대상을 찾기’

### 5.1 기본 기능

- **담당업무로 후보 찾기**: “출장 여비 정산 담당자” 같은 요청을 부서·담당업무 검색 조건으로 정리한다. 화면에서 확인한 정보와 사용자가 명시적으로 등록한 연락처 범위 안에서만 후보를 찾는다.
- **추천 이유 표시**: 후보의 담당업무 중 일치하는 문장을 보여 준다. ‘담당자 확정’ 대신 ‘담당자 후보’로 표현한다. 근거가 없으면 후보를 만들지 않는다.
- **동명이인 비교**: 기관·부서·직급·화면에 공개된 연락처로 구분한다. 직급도 같은 경우가 있으므로 이름+직급만으로 확정하지 않는다.
- **부서·역할별 수신자 준비**: 선택 부서에서 필요한 역할·사람을 고르고 구성원 목록을 검토한다. 목록 일부만 읽었다면 ‘부서 전체’로 표시하지 않는다.
- **업무 연락으로 이어가기**: 확인한 대상과 사용자가 선택한 목적을 새 쪽지/연락 준비로 넘긴다. 초안에는 업무상 필요한 사실만 포함한다.

### 5.2 친구와의 구분

친구에서는 ‘이미 아는 사람에게 무엇을 연락할지’, 조직도에서는 ‘이 일을 누구에게 연락할지’를 먼저 해결한다. 같은 사람 정보·수신자 묶음 컴포넌트를 재사용하되 기본 카드와 행동의 순서를 다르게 한다.

타 기관 조회, 가상 스크롤, 접힌 부서는 수집 범위를 제한한다. ‘기관 전체를 검색했습니다’라는 문구는 전체 범위를 실제로 확보했을 때만 허용한다. 전체 조직도 동기화·조건 그룹 자동 갱신·온톡 그룹 쓰기는 후속 검증 대상으로 둔다.

## 6. 대화: ‘흐름 복구 → 업무 정리 → 답변 작성’

### 6.1 대화 목록과 대화창을 구분한다

대화 목록에서는 모든 방을 자동으로 요약하지 않는다. 선택한 방의 확인 가능한 제목·참여자와 이미 확보한 대화/업무만 연결한다. 본문을 확보하지 못했다면 “대화창을 열어 읽은 범위를 정리하세요”를 보여 준다. 목록 미리보기만으로 결론이나 업무를 추출하지 않는다.

대화창에서는 **내용 파악과 답변 작성이 함께 필요한 작업**이다. 기본은 ‘흐름·답변·업무’의 세 작업으로 구성한다. 타이핑할 때마다 화면을 강제로 교체하지 않고, ‘답변 작성’ 선택 또는 확인된 입력 상태에 따라 답변 영역을 강조한다. 내용 파악 결과와 작성 중 초안을 함께 보존한다.

### 6.2 추천 기능과 우선순위

| 기능 | 사용자에게 주는 도움 | 입력/근거 | 우선순위 |
|---|---|---|---|
| 최근 흐름 요약 | 대화에 다시 참여할 때 진행 상황 파악 | 사용자가 선택한 메시지 또는 현재 확보한 메시지 범위 | 필수 |
| 결정·검토·미결 구분 | 제안과 확정 사항을 혼동하지 않음 | 발언자·시각·관련 메시지. 확정 근거가 없으면 미결 표시 | 필수 |
| 내게 온 질문·요청 후보 | 답변할 일을 놓치지 않음 | 내 식별자·멘션·명시된 요청. 식별 실패 시 ‘질문 후보’ | 필수 |
| 맥락에 맞는 답변 초안 | 질문에 대한 짧은 답·확인 질문 작성 | 명시적으로 고른 대화 범위와 사용자 답변 의도 | 필수 |
| 문장 다듬기 | 짧고 명료하고 정중한 표현 | 현재 초안 또는 사용자가 선택한 초안 문장 | 필수 |
| 할 일 후보 등록 | 대화의 후속 작업을 관리 | 근거 메시지와 명시된 담당자·기한 | 다음 단계 |
| 긴 대화를 쪽지로 정리 | 공식 공유·자료 요청으로 전환 | 선택 메시지·확인한 결정·명시적 수신자 선택 | 다음 단계 |
| 대화 내용 질문하기 | “제출일이 언제였지?” 등의 확인 | 확보 범위 내 검색, 출처 메시지 | 다음 단계 |
| 파일과 관련 업무 연결 | 자료를 업무와 함께 확인 | 실제 확보한 파일·메시지 연결 | 후속 |

답변 의도 예: **확인·동의 / 일정 협의 / 추가 질문 / 진행 상황 공유**. 기본 문체는 짧은 업무 대화이며 쪽지의 인사말·맺음말을 매번 붙이지 않는다. 개인/그룹 여부와 참여자 정보를 확인했을 때만 표현을 조절한다. 사용자가 고르지 않은 날짜·약속·담당자를 초안에 채우지 않는다.

### 6.3 범위·변화·초안 처리

- ‘선택 메시지’, ‘현재 확보한 구간’, ‘저장한 구간’ 중 실제 사용한 범위를 표시한다. 시작·끝 시각을 읽지 못하면 메시지 수와 범위 불확실 표시를 사용한다.
- 화면에 안 보이는 과거 발언, 읽음 이후 모든 메시지, 대화방 전체를 읽었다고 주장하지 않는다. ‘놓친 내용’은 읽음 경계가 확인된 경우에만 쓰고 그 외에는 ‘최근 확보 내용’이라고 표시한다.
- 발언 수정·삭제를 감지하면 관련 요약과 업무 근거를 다시 확인한다. 결론을 자동으로 덮어쓰지 않고 변경된 근거를 표시한다.
- 새 메시지가 왔다고 진행 중인 초안이나 요약 화면을 바꾸지 않는다. ‘새 내용 있음 → 요약 갱신’으로 이어진다.
- 초안이 근거로 삼은 뒤 새로운 메시지가 생기면 검토 시 알린다. 대화방이 바뀌면 이전 방 초안을 새 방에 넣지 않는다.
- 입력 반영은 대화창 입력·줄바꿈·본문 재읽기 검증 후 제공한다. 쪽지의 바이트 규칙이나 입력 어댑터를 대화에 그대로 적용하지 않는다.
- 첫 단계는 초안 복사 또는 검증된 입력 반영까지다. 사이드카에서 대화 전송을 자동으로 실행하지 않는다. Enter가 실제 전송인지 줄바꿈인지도 시험 없이 가정하지 않는다.

## 7. 쪽지: 목록·읽기·작성의 세 작업

### 7.1 쪽지 목록

받은·보낸·보관 쪽지함은 목록 문맥으로 구분한다. 기본 내용은 ‘현재 쪽지함 / 보관 자료 검색 / 연결된 업무’다. 목록에서 본문이 읽히지 않으면 내용을 분석하지 않고 쪽지 열기를 안내한다. 검색 결과는 온톡 전체 쪽지와 로컬 보관 자료를 혼동하지 않도록 ‘사이드카에 보관된 자료’로 표시한다.

받은 쪽지함의 회신 필요 후보는 **실제 읽어 보관한 내용**에서만 제공한다. 보낸 쪽지함에서는 전달 내용·관련 업무를 보여 주되 읽음·도착·회신 여부는 온톡에서 확인하지 못하면 추정하지 않는다. 보관함은 원문·첨부 확보 상태를 구분한다. 보낸/보관 상세는 현재 파서가 지원하지 않으므로 별도 구조 검증 후 활성화한다.

### 7.2 받은 쪽지: 읽기·이해 지원

기본 순서는 **핵심 요약 → 요청/질문 → 기한·근거 → 확인할 점 → 첨부·관련 업무**다. 원문은 항상 접근 가능하게 둔다.

- 요약과 요청은 원문의 근거 문장으로 돌아갈 수 있어야 한다.
- “내가 해야 할 일”은 수신자·담당자를 확인할 수 있는 경우에만 표현한다. 공지·다중 수신 쪽지는 ‘요청/할 일 후보’로 표시한다.
- 이해하기 어려운 문장 풀어쓰기·선택 문장 질문을 제공한다. 현재 쪽지와 사용자가 추가한 자료만 참조한다.
- 기한이 없으면 ‘원문에 기한 없음’, 연도 추정은 기존 표시를 유지한다.
- 첨부는 파일명 확인·파일 확보·내용 추출을 서로 다른 상태로 표시한다.
- ‘답장 준비’는 읽기 도구의 보조 행동이다. 실제 작성창으로 이동한 뒤 작성 화면이 우선되며 원문은 참고 영역으로 남는다.

### 7.3 작성 공통: 내용 생성·에디팅 지원

기본 순서는 **작성 목적 → 현재 초안 → 생성/편집 도구 → 변경 검토 → 최종 점검·반영**이다. 원문 요약·할 일 등록을 기본 작업으로 두지 않는다.

생성 도구는 요청·공지·문의·보고의 내용 뼈대, 핵심 사실 입력, 템플릿·문구·인용을 제공한다. 편집 도구는 문장 다듬기·맞춤법 제안·간결하게·정중하게·항목화·선택 문장 수정·원문 요청에 대한 누락 점검을 제공한다. 맞춤법 검사가 모델 제안이면 확정된 오류 검사처럼 표시하지 않는다.

AI 결과는 **현재 글 / 제안된 글**로 비교하며 사용자가 선택한 뒤 편집 초안에 반영한다. 되돌리기를 제공하고, 선택 문장 수정 시 그 밖의 문장과 원문 인용을 보존한다. 선택 범위를 못 읽으면 사이드카 편집기에서 사용자가 범위를 정한다. 반영할 때는 온톡에서 사용자가 직접 수정한 최신 글과 충돌하는지 다시 읽는다.

최종 점검은 실제 수신자·자리 표시·명시한 첨부 포함 여부·본문 바이트·예약·SMS 상태를 다룬다. 예약/SMS가 없는 대화 답변과 동일한 점검 UI를 사용하지 않는다. 아직 읽지 못하는 첨부 목록은 ‘확인 필요’로 두며 첨부가 자동 전송된다고 표시하지 않는다.

### 7.4 작성 종류별 차이

| 종류 | 추가 지원 | 보존/점검 사항 |
|---|---|---|
| 새 쪽지 | 목적·대상·요청사항·기한·연락 방법으로 내용 구성; 목적별 템플릿 | 현재 받은 쪽지를 자동 참고하지 않음. 사용자가 자료를 추가한 경우만 사용 |
| 답장 | 원문의 요청·질문별 응답 체크, 수락/조정/질문 초안 | 원문 연결 확인, 발신자와 실제 수신자 비교, 온톡이 넣은 인용 보존 |
| 전체답장 | 공동으로 공유할 답변·특정인에게만 필요한 내용 점검 | 실제 작성창의 수신자를 기준으로 확인. 수신 인원만 보고 명단을 복원하지 않음 |
| 전달 | 전달 이유·수신자가 해야 할 일·배경 설명 작성 | 새 수신자 확인, 원문과 소개 문장 분리, 원문/첨부 포함 상태 확인 |
| 종류 불명 작성창 | 일반 생성·에디팅·점검 | ‘쪽지 작성’으로 표시. 답장 원문·전체 수신자·전달 목적을 추정하지 않음 |

단순 제목 문구만으로 원문 쪽지와 작성창을 연결하지 않는다. 사이드카가 시작한 전환의 출처와 새 작성창의 관찰 결과가 일치할 때 연결한다. 온톡에서 직접 연 창은 명확한 출처가 없으면 사용자가 참고 원문을 선택하게 한다.

## 8. 사이드카 화면 구조와 전환 규칙

### 8.1 공통 외곽, 작업별 내용

- **머리줄**: sAIde, 현재 작업명, 공통 검색·업무·관리, 접기.
- **문맥 표시**: `친구 · 선택한 사람`, `조직도 · 선택 부서`, `대화 · 방 이름`, `받은 쪽지 · 발신자`, `답장 작성 · 수신자`. 대상을 못 읽으면 확인되지 않았다고 표시한다.
- **본문**: 해당 작업의 요약/사람/담당자/편집 컴포넌트. 활성 문맥에서 필요한 기능만 표시한다.
- **주요 행동**: 현재 작업에 필요한 버튼 1개를 우선한다. 선택 없음·범위 불명·반영 불가 상태에서는 실행을 막고 해결 방법을 제시한다.
- **접힌 도구**: 펼치기·현재 작업의 대표 기능·공통 도구. 대표 기능은 친구=연락 준비, 조직도=담당자 찾기, 대화=흐름/답변, 쪽지 읽기=요약, 작성=다듬기다.

현재 360 DIP 기본 폭·창 높이 추적·44 DIP 접힌 도구를 재사용한다. 360 DIP에서 긴 수신자·문맥명은 줄바꿈/확장 상세로 처리하고, 편집 도구가 부족하면 같은 문맥을 유지하는 확장 편집창을 연다. 짧은 창에서는 본문만 스크롤하고 문맥·핵심 행동은 접근 가능하게 둔다.

### 8.2 전환 우선순위

1. 계정 미확인·로그아웃·계정 전환 → 연결 상태 화면. 이전 계정 문맥·초안 표시를 중단한다.
2. 제외 메뉴 또는 부모 작업과 연결되지 않은 제외 창 → 전용 본문을 숨기고 접힌 공통 도구만 제공한다. 이전 쪽지 내용이 남지 않는다. 작성창의 수신자 추가처럼 확인된 보조 창은 다음 규칙으로 처리한다.
3. 수신자/예약 같은 현재 작업의 보조 대화상자 → 부모 작성 문맥 유지, 본문 반영을 일시 비활성화한다. 사용자 검색 메뉴의 전용 기능으로 확장하지 않는다.
4. 실제 활성 쪽지 작성창 → 작성 종류별 지원.
5. 실제 활성 쪽지 읽기창 → 해당 쪽지 읽기 지원.
6. 실제 활성 대화창 → 해당 방의 흐름·답변 지원.
7. 메인 창 → 활성 메뉴와 선택 대상에 맞는 지원.
8. 창만 확인되고 내용/메뉴를 판별하지 못함 → ‘현재 화면 확인 중/선택 필요’. 다른 창의 내용으로 대체하지 않는다.

위 우선순위는 **현재 대상 내부에서** 적용한다. 다른 곳에 작성창이 열려 있다는 이유로 현재 친구 화면을 작성 화면으로 바꾸지 않는다. 사이드카와 그 확장 편집창에 포커스가 와도 마지막 온톡 문맥을 유지한다. 보조 대화상자 관계를 확인하지 못하면 입력 실행을 막는다.

새 문맥이 확인되는 즉시 이전 대상의 본문·반영 버튼을 무효화한다. 일반 메뉴 전환은 두 번 연속 일치 관찰 또는 검증된 선택 상태로 확정해 깜박임을 줄인다. 로그인·계정 변경·제외 화면은 안정화 대기 없이 이전 내용을 숨긴다. 늦게 끝난 AI 결과는 원래 문맥에만 저장하며 현재 다른 문맥에는 표시하지 않는다.

## 9. 구현 설계

### 9.1 책임 분리

```text
OnTalkDock ── 창의 위치·부착 대상
     │ 동일한 대상 식별자로 연결
OnTalkContextWatcher / 페이지별 Reader ── 메뉴·선택·작업·지원 가능 기능 관찰
     ↓
ContextResolver ── 표시 문맥 확정·변경 이력·세대 번호
     ↓
SidecarPolicy ── 문맥 + 선택 상태 + 가능한 기능 → 화면 구성·허용 행동
     ↓
Context별 ViewModel/View ── 친구 / 조직도 / 대화 / 쪽지 목록 / 읽기 / 작성
     ↓ 명시적으로 검토한 실행 요청
반영 어댑터 ── 실제 대상·현재 본문 재확인 → 반영 → 결과 재확인
```

부착 대상과 표시 대상은 동일한 `WindowSessionId`를 쓴다. 닫힌 뒤 재사용되는 HWND는 새 세션으로 식별한다. Core는 HWND/MSAA 노드 대신 중립적인 세션 식별자와 관찰 결과만 받는다.

### 9.2 문맥 계약

| 필드 | 의미 |
|---|---|
| `AccountScope` | 기존 확인한 계정 범위. 기관 구분이 필요하면 확인된 기관도 포함 |
| `WindowSessionId` | 어댑터가 부여한 창 수명 식별자. 실제 HWND 연결은 Automation이 보관 |
| `Surface` | Main / NoteRead / NoteCompose / Chat / Auxiliary / Excluded / Unknown |
| `MainMenu` | Friends / Organization / Conversations / Notes / Excluded / Unknown |
| `Activity` | Browse / Person / Group / Department / Read / Draft / Verify |
| `ComposeKind` | New / Reply / ReplyAll / Forward / Unknown |
| `Selection` | 선택 사람·부서·그룹·대화방·쪽지. 신원 확인 수준도 포함 |
| `SourceReference` | 사용자가 선택하거나 검증된 전환으로 연결한 원문. 없는 경우 null |
| `Coverage` | 확보한 목록/메시지 범위, 관찰 시각, 완전/부분/불명 |
| `Capabilities` | 지원/부분 지원/불가인 기능과 근거·제한 이유 |
| `ContextRevision` | 대상·계정·선택·작업 변경 시 증가. 비동기 결과의 유효성 확인 |

창/메뉴 종류는 AI가 결정하지 않는다. 관찰한 페이지 경로, 선택 상태, 고유 작업 요소로 판별한다. 메인 창의 페이지 경로는 메뉴가 바뀌어도 같으므로 **활성 메뉴 신호를 별도로** 읽어야 한다. 선택 신호가 없는 경우 고정 위치·텍스트 하나로 확정하지 않고 미확인으로 둔다.

### 9.3 필요한 코드 변경

| 영역 | 변경 | 재사용 |
|---|---|---|
| Automation | `OnTalkContextWatcher`, `MainWindowParser`, `ChatWindowParser`; 쪽지 작성 종류 판별 확장; 선택 상태·대화상자 부모 관계·수명 추적 | MSAA 읽기, `AccNode`, 받은 쪽지/작성 파서, 수신자·예약 도구 |
| Core | 문맥/선택/범위 계약, `ContextResolver`, `SidecarPolicy`, 출처·버전 조건, 초안 세션 규칙 | 업무·근거 검증, 쪽지 바이트·시각 규칙 |
| App | `PanelWindow`에서 고정 `NoteView` 대신 문맥별 View; 표시/부착 대상 통합; 작성 지원의 패널 내 진입 | 테마·도킹·트레이·검색/업무/관리 창 |
| AI | 사람 탐색 조건 해석, 대화 범위 요약·결정/질문 근거, 목적별 작성; 제안 비교 | 로컬 Ollama 연결·취소·근거 대조 |
| Storage | 초안 세션·출처 범위·사람 연결의 신원 수준; 대화 보관은 별도 옵션/보존 설계 뒤 추가 | 계정별 암호화 저장소·업무·문구·파일 |

쪽지 수집 감시와 현재 문맥 감시는 분리한다. 기존 받은 쪽지 수집 정책은 유지하되, 수집된 다른 창의 내용은 현재 화면으로 대체하지 않는다. `_notNotePages`는 수명 내 영구 제외 대신 경로 변화/유효기간으로 다시 검사한다.

창 위치 감시는 기존 짧은 주기를 유지하고, 내용 읽기는 백그라운드에서 활성 대상 위주로 수행한다. 메인 트리 전체를 위치 감시의 100ms마다 읽지 않는다. 메뉴 신호의 저비용 조회 가능 여부를 확인한 뒤 내용 폴링 간격을 정한다. 문맥 표시 목표는 안정화 후 2초 이내이며 기존 메인 트리 1.5초 측정은 목표 달성의 증거가 아니다.

### 9.4 초안·근거·충돌

- 초안 키는 `계정 + DraftSessionId`다. 작성 종류·출처·대상은 속성으로 보관한다. 창이 둘이면 같은 원문·수신자여도 독립 세션이다.
- 대화방 식별자를 확보하면 초안 연결에 사용한다. 제목/참여자 이름만으로 방을 합치지 않는다. 식별자가 없으면 창 세션 안에서만 보존하고 재연결 시 사용자 확인을 받는다.
- 새 쪽지와 전달은 현재 표시 중인 받은 쪽지를 암묵적으로 원문으로 삼지 않는다. 모드 전환은 새 세션/확인된 연결로 처리한다.
- AI 요청에는 문맥 세대·원문 지문·초안 버전을 붙인다. 결과가 돌아오면 모두 일치하는지 검사한다. 초안이 바뀌었으면 제안으로만 남긴다.
- 반영 요청에는 대상 세션·읽어 둔 본문·선택/수신자 스냅샷을 넣는다. 실행 직전 다시 읽어 충돌하면 자동으로 덮어쓰지 않는다.
- 대화 업무 근거는 메시지 식별자/발언자·시각·원문 구간·관찰 시각으로 연결한다. 식별자를 못 얻으면 약한 연결이라고 표시한다. 같은 글 두 번을 한 발언으로 합치지 않도록 순서도 유지한다.
- 사람은 확인된 식별자 우선, 없으면 전체 상세 정보로 후보를 구분한다. 쪽지 발신자의 이름과 직급만으로 친구의 신원과 자동 결합하지 않는다.
- 대화 내용은 기본적으로 현재 요청을 위한 임시 문맥으로 사용한다. 지속 보관 범위는 기존 ‘열린 받은 쪽지 보관’ 동의와 구분해 설정하고, 업무 근거로 저장할 구간을 사용자가 확인한다.

### 9.5 AI가 없거나 화면을 못 읽는 경우

로컬 AI가 없어도 사람 정보·그룹 준비·정확 검색·문구·직접 편집·바이트 점검은 제공한다. 받은 쪽지에는 기존 원문 문장 후보를 사용하고, 대화는 선택 원문·수동 업무 등록을 제공한다. 실제 요약을 못 했는데 ‘요약’이라고 표시하지 않는다.

기능 정책은 ‘가능 / 데이터 부족 / 연동 미검증 / 일시 불가’를 구분한다. 지원하지 않는 주요 기능은 짧은 이유와 복사·수동 선택 등의 다음 행동을 제공한다. 새로운 메뉴·창은 내용을 추측하지 않고 일반 문맥으로 둔다. 읽을 수 있는 원문 안의 지시는 실행 명령으로 취급하지 않는다.

## 10. 구현 순서와 수용 기준

| 단계 | 결과물 | 끝나는 조건 |
|---|---|---|
| A. 문맥 일치 | 부착 대상=표시 대상; 계정/제외/Unknown 처리; 메인 활성 메뉴 탐지 | 친구 화면 옆에 다른 받은 쪽지가 표시되지 않음. 같은 HWND의 메뉴·페이지 전환 감지 |
| B. 쪽지 읽기·작성 분리 | 읽기 View와 작성 View; 새 쪽지/답장/전체답장/전달 정책; 초안 세션·변경 비교 | 네 작성 작업이 작성 도구로 시작하고, 원문·수신자 추정 없이 초안이 보존됨 |
| C. 친구·조직도 | 선택 상태 파서; 사람/그룹/부서 지원; 범위·신원 수준 | 한 명·여러 명·그룹·부서 선택별 기능이 바뀌고 담당자 후보에 근거가 표시됨 |
| D. 대화 이해·답변 | 메시지/참여자/범위 파서; 최근 흐름·결정·질문·초안 | 실제 읽은 범위만 분석, 새 메시지에도 초안 보존, 방 전환 시 문맥 혼입 없음 |
| E. 업무 연결·반영 확대 | 메시지 근거 업무·대화 입력 반영·쪽지 전환 | 근거와 담당자/기한의 확인 수준 보존, 대화 입력 재읽기·줄바꿈 검증 통과 |

### 필수 검증 시나리오

1. 받은 쪽지 A를 열어 둔 채 친구→조직도→대화→쪽지 메뉴를 이동한다. 제목·카드·주요 행동이 해당 메뉴에 맞고 A의 요약이 남지 않는다.
2. 메인 쪽지 목록에서는 목록 지원, 받은 쪽지 상세에서는 읽기 지원, 새 쪽지·답장·전체답장·전달에서는 각각 작성 지원이 나온다.
3. 받은 쪽지 A/B와 작성창 C를 오간다. 패널 부착 대상과 표시 대상이 항상 같고 저장 수집 정책과 표시 선택이 섞이지 않는다.
4. 같은 창에서 쪽지 내용/페이지가 바뀐다. 비쪽지 캐시 때문에 문맥 변화를 놓치지 않는다.
5. 같은 원문에 대한 답장·전체답장·전달과 새 쪽지 두 개의 초안을 각각 유지한다. 하나를 열거나 닫아도 다른 초안을 덮어쓰지 않는다.
6. 분석 중 메뉴·사람·방·계정을 바꾼다. 이전 결과가 새 화면에 유입되지 않는다. 로그인·로그아웃 때 본문과 입력 기능이 즉시 비활성화된다.
7. 친구·조직도의 동명이인, 이름·직급까지 같은 사람, 선택 없음/다중 선택/부분 목록을 시험한다. 자동 동일인 결합·부서 전체 추정이 없다.
8. 대화에서 제안→검토→확정→변경 메시지를 시험한다. 결정 근거가 표시되고 미확정은 확정으로 바뀌지 않는다. 새 메시지는 기존 초안을 교체하지 않는다.
9. 대화방 이름이 같거나 참여자가 비슷한 두 방을 오간다. 범위·업무·초안이 섞이지 않고, 내 식별자가 불명확하면 ‘내게 온 요청’으로 단정하지 않는다.
10. 전체답장 수신자 명단/전달 첨부 포함 여부를 못 읽으면 ‘확인 필요’다. 수신 인원만으로 명단을 생성하지 않는다.
11. 온톡에서 직접 글을 고친 후 오래된 초안을 반영한다. 충돌을 감지하고 기존 글·인용을 보존한다. 생성/수정 제안에는 비교·되돌리기가 있다.
12. 사용자 검색·알리미로 이동하면 이전 작업 본문을 숨긴다. 작성 과정의 수신자 추가 대화상자에서는 부모 작성 문맥을 유지하되 입력 반영은 막는다.
13. AI 미실행/시간초과, 읽기 실패, 문맥 불명, 100/125/150% 배율, 짧은 창, 접기/펼치기를 시험한다. 대안 행동과 명확한 확인 수준이 유지된다.

파서·정책·초안 격리·늦은 결과·반영 충돌은 단위 테스트로, 실제 선택 신호·메뉴 전환·대화 범위·입력·도킹은 온톡 실화면으로 검증한다. 실제 메시지 발송은 이 분석·설계 작업에 포함하지 않는다.

## 11. 설계 결정

첫 구현은 **문맥 일치와 쪽지 읽기/작성 분리**부터 진행한다. 이는 기존 기능을 활용하면서 현재 문제를 직접 해결한다. 친구·조직도는 대상 선택을 기준으로 분리하고, 대화는 **최근 흐름·결정/질문·짧은 답변**을 최소 기능으로 시작한다. 전체 이력 수집·모든 방 자동 분석·조직도 전체 동기화는 검증 없이 전제하지 않는다.

사이드카의 일관성은 모든 화면에서 같은 기능을 보여 주는 데서 얻지 않는다. **같은 위치·같은 문맥 표시·같은 검토/반영 규칙 안에서, 현재 작업에 맞는 도움을 제공하는 것**으로 정의한다.
