# 연동 기술검증 결과 (P0, 진행 중)

- 작성일: 2026-10-03, Asia/Seoul
- 대상: 온톡 5.4.3 (Electron 7.3.3 / Chromium 78), Windows 11 Pro
- 도구: [tools/OnTalk.Probe](../tools/OnTalk.Probe/Program.cs)
- 열람 범위: 이 문서의 결과는 모두 요소 개수·역할·글자 수 집계다. 이름·본문은 출력하지 않았다. 온톡에 입력·클릭은 하지 않았다.

## 확인한 것

| 항목 | 결과 | 근거 |
|---|---|---|
| 접근성 트리 읽기 | **가능.** 온톡 재시작·실행 옵션 변경 없이 읽힌다 | 메인 창에서 요소 444개, 깊이 16 |
| 읽기 속도 | MSAA(IAccessible) 직접 조회 시 메인 창 전체 1.5초, 대화창(요소 50개) 0.1초 | `stats` 1회 실행 |
| UIA 경유 | **사용하지 않는다.** 요소별 조회는 480개에 21초, 하위 트리 일괄 캐시 조회는 2분 넘게 끝나지 않았다 | 조사 도구 쪽 CPU만 소모, 온톡은 계속 응답 |
| 창 종류 식별 | 문서 요소의 값이 페이지 경로다 (`windows/renderer/app.html`, `windows/chat/app.html`) | 개인정보 없이 창 종류를 구분할 수 있다 |
| 미리 만들어 둔 창 | 보이지 않는 대화창(360x660)이 1개 대기 중 | 창 생성 이벤트만으로 "쪽지를 열었다"고 판단하면 안 된다. 표시 여부를 함께 본다 |
| 텍스트 노출 | 메인 창 statictext 106개가 모두 이름을 가진다 | 화면 글자가 요소 이름으로 나온다 |

## 계획 검토 문서와 달라진 점

[plan-review.md](plan-review.md)는 "UIA 요소 2개, MSAA 하위 노드 0개"로 기록했다. 이번에는 활성화 신호(`activate`)를 보내기 전에 이미 트리가 읽혔다. 원인은 확인하지 못했다. 첫 조회 때 Windows의 접근성 프록시가 Chromium의 스크린리더 감지에 응답해 켜졌을 가능성이 있으나 추정이다. 그래서 사이드카는 연결할 때마다 `activate` 신호를 명시적으로 보내고, 트리가 비어 있으면 연결 불확실 상태로 둔다.

## 아직 확인하지 못한 것

1. 받은 쪽지 창의 구조: 발신자·시각·본문·첨부가 어떤 요소로 나오는지. 테스트 쪽지를 열어야 한다.
2. 쪽지 작성 창의 구조: 수신자 목록, 본문 입력창, 바이트 표시, 예약·SMS 선택 상태.
3. 입력 반영: 붙여넣기로 넣은 본문이 바이트 표시에 반영되는지.
4. 쪽지 목록의 가상 스크롤 범위와 쪽지 식별자 노출 여부.
5. 온톡을 재시작한 직후에도 `activate`만으로 트리가 켜지는지.
6. 보안 에이전트(GsNarMon, uMonitor)가 입력 주입을 막는지.
7. 조직 승인: 원문 로컬 보관, 접근성 경유 수집의 허용 여부. 기술 문제가 아니므로 사용자 확인 사항이다.
